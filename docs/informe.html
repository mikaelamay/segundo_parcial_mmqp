Resumen del proyecto. MediControl es una aplicación web desarrollada con Flask que implementa el patrón Application Factory, tres Blueprints independientes, modelos relacionados con SQLAlchemy, migraciones versionadas con Flask-Migrate y una interfaz responsiva construida sobre Bootstrap 5. La base de datos utilizada es SQLite, tal como solicita el enunciado del examen.
Sección 1

Introducción y objetivos

La empresa MediControl necesita administrar la información de sus médicos, sus pacientes y las citas que se agendan diariamente. Para resolver esta necesidad se construyó un sistema monolítico modular: una sola aplicación desplegable, pero organizada internamente por módulos de negocio independientes (médicos, pacientes y citas), cada uno con sus propias rutas y plantillas.

El backend se implementó con Flask, el acceso a datos con SQLAlchemy, el control de versiones del esquema con Flask-Migrate y la interfaz con Bootstrap 5. La base de datos es SQLite, almacenada en el archivo instance/medicontrol.db, conforme al requerimiento de la Parte 1 del examen.

Objetivos

  • Implementar el patrón Application Factory mediante create_app().
  • Crear y registrar los Blueprints bp_medicos, bp_pacientes y bp_citas con sus prefijos de URL.
  • Definir los modelos y sus relaciones uno a muchos, y versionar el esquema con migraciones.
  • Construir los CRUD completos y las plantillas que heredan de una plantilla base común.
  • Verificar el funcionamiento con datos de prueba y operaciones reales (alta, edición, consulta y baja).

Alcance y decisiones de diseño

El sistema cubre el ciclo completo de gestión: registro de médicos y pacientes, agenda de citas, edición y eliminación controlada. Se incorporaron validaciones adicionales para evitar citas duplicadas de un mismo médico en la misma fecha y hora, y para impedir la eliminación de médicos o pacientes que tengan citas asociadas, protegiendo así la integridad referencial.

La interfaz incluye un panel principal con indicadores, búsqueda de médicos y pacientes, filtros de citas por fecha y médico, mensajes de confirmación y alertas de error. Todos los recursos de Bootstrap se guardaron localmente en app/static/vendor, por lo que la aplicación funciona sin depender de una conexión a Internet.

Organización del documento. Las secciones 3 a 6 corresponden exactamente a las cuatro partes del examen. Cada una incluye una explicación breve y las capturas de pantalla que evidencian su implementación.

Sección 3 · Parte 1

Arquitectura y configuración

Application Factory, Blueprints con prefijos y configuración de SQLite.

3.1. Patrón Application Factory

Toda la aplicación se construye dentro de la función create_app() ubicada en app/__init__.py. Esta función recibe una clase de configuración, crea la instancia de Flask, inicializa las extensiones y registra los Blueprints. Gracias a este patrón, la aplicación puede crearse con configuraciones distintas (por ejemplo, pruebas o producción) sin duplicar código.

app/__init__.py
def create_app(config_class=Config):
    app = Flask(__name__, instance_relative_config=True)
    app.config.from_object(config_class)

    # Carpeta instance/ para la base SQLite
    os.makedirs(app.instance_path, exist_ok=True)

    # Inicialización de extensiones
    db.init_app(app)
    migrate.init_app(app, db)

    # Registro de modelos para SQLAlchemy y Flask-Migrate
    from app import models

    # Registro de Blueprints con sus prefijos
    from app.blueprints.medicos import bp_medicos
    from app.blueprints.pacientes import bp_pacientes
    from app.blueprints.citas import bp_citas

    app.register_blueprint(bp_medicos, url_prefix="/medicos")
    app.register_blueprint(bp_pacientes, url_prefix="/pacientes")
    app.register_blueprint(bp_citas, url_prefix="/citas")

    return app

3.2. Blueprints registrados

Cada módulo de negocio vive en su propio paquete dentro de app/blueprints/. El archivo __init__.py define el Blueprint y el archivo routes.py contiene sus rutas. De este modo, el monolito queda dividido en módulos con bajo acoplamiento.

Blueprint Prefijo Archivo de rutas Responsabilidad
bp_medicos /medicos blueprints/medicos/routes.py CRUD de médicos y búsqueda por especialidad
bp_pacientes /pacientes blueprints/pacientes/routes.py CRUD de pacientes y validación de teléfono
bp_citas /citas blueprints/citas/routes.py Agenda de citas, filtros y control de choques de horario

3.3. Configuración de SQLite

La cadena de conexión se define en config.py. Flask crea automáticamente la carpeta instance/ y la base de datos se genera al aplicar las migraciones. También se permite sobrescribir la URL mediante la variable de entorno DATABASE_URL.

config.py
class Config:
    SECRET_KEY = os.environ.get("SECRET_KEY", "medicontrol-clave-de-desarrollo-2026")

    # El examen solicita SQLite como motor de base de datos.
    SQLALCHEMY_DATABASE_URI = os.environ.get(
        "DATABASE_URL",
        f"sqlite:///{BASE_DIR / 'instance' / 'medicontrol.db'}",
    )
    SQLALCHEMY_TRACK_MODIFICATIONS = False
    SQLALCHEMY_ENGINE_OPTIONS = {"pool_pre_ping": True}

3.4. Estructura del proyecto

La organización separa configuración, modelos, Blueprints, plantillas y recursos estáticos. Las migraciones y el script de datos de prueba se mantienen en la raíz para facilitar la puesta en marcha.

3.5. Aplicación en ejecución

Al iniciar el servidor con flask --app run.py run, la ruta principal / presenta el panel de control. En él se muestran los indicadores de médicos, pacientes y citas, las próximas citas ordenadas por fecha y hora, y accesos rápidos a las operaciones más frecuentes.

La interfaz es responsiva y utiliza una barra de navegación con acceso directo a los tres módulos. Los colores y componentes fueron personalizados sobre Bootstrap 5 para darle una identidad visual coherente con el sector salud.

Resultado de la Parte 1. La aplicación se crea mediante create_app(), los tres Blueprints están registrados con los prefijos solicitados y SQLite quedó configurado como motor de persistencia. La estructura modular permite agregar nuevos módulos (por ejemplo, especialidades o historiales) sin alterar los existentes.
Sección 4 · Parte 2

Modelos y migraciones

Entidades Médico, Paciente y Cita, relaciones uno a muchos y versionado del esquema.

4.1. Modelos implementados

Los modelos se organizaron en un paquete (app/models/) con un archivo por entidad. Todos heredan de db.Model y declaran explícitamente el nombre de su tabla.

Modelo Tabla Campos Relación
Medico medicos id, nombre, especialidad Un médico tiene muchas citas
Paciente pacientes id, nombre, telefono Un paciente tiene muchas citas
Cita citas id, fecha, hora, medico_id, paciente_id Pertenece a un médico y a un paciente
app/models/medico.py · paciente.py · cita.py
class Medico(db.Model):
    __tablename__ = "medicos"
    id = db.Column(db.Integer, primary_key=True)
    nombre = db.Column(db.String(120), nullable=False)
    especialidad = db.Column(db.String(120), nullable=False)
    citas = db.relationship("Cita", back_populates="medico")

class Paciente(db.Model):
    __tablename__ = "pacientes"
    id = db.Column(db.Integer, primary_key=True)
    nombre = db.Column(db.String(120), nullable=False)
    telefono = db.Column(db.String(30), nullable=False)
    citas = db.relationship("Cita", back_populates="paciente")

class Cita(db.Model):
    __tablename__ = "citas"
    id = db.Column(db.Integer, primary_key=True)
    fecha = db.Column(db.Date, nullable=False)
    hora = db.Column(db.Time, nullable=False)
    medico_id = db.Column(db.Integer, db.ForeignKey("medicos.id"), nullable=False)
    paciente_id = db.Column(db.Integer, db.ForeignKey("pacientes.id"), nullable=False)
    medico = db.relationship("Medico", back_populates="citas")
    paciente = db.relationship("Paciente", back_populates="citas")

4.2. Relaciones e integridad

La relación se declara en ambos sentidos con back_populates: desde Medico y Paciente se accede a la colección citas, y desde Cita se accede al medico y al paciente. Las claves foráneas medico_id y paciente_id son obligatorias y cuentan con índices para acelerar las consultas.

Además de la integridad declarada en la base de datos, la capa de aplicación impide eliminar un médico o un paciente que tenga citas asociadas, y valida que no exista otra cita para el mismo médico en la misma fecha y hora.

4.3. Migraciones con Flask-Migrate

Se inicializó el repositorio de migraciones, se generó la migración inicial a partir de los modelos y se aplicó sobre SQLite. La revisión generada es 2a61b8b3acee. Los comandos utilizados fueron:

Terminal — inicialización y aplicación de migraciones
# 1) Inicializar el repositorio de migraciones
flask --app run.py db init

# 2) Generar la migración inicial comparando los modelos con la BD
flask --app run.py db migrate -m "Esquema inicial: medicos, pacientes y citas"

# 3) Aplicar los cambios a la base de datos
flask --app run.py db upgrade

# 4) Verificar la revisión activa
flask --app run.py db current

Para comprobar que las migraciones funcionan desde cero, se aplicó la misma revisión sobre una base temporal (/tmp/medicontrol_demo.db). La salida confirma la creación de las tablas medicos, pacientes, citas y alembic_version.

4.4. Esquema resultante en SQLite

El esquema generado incluye las tres tablas de negocio, sus claves primarias, las claves foráneas de citas y los índices correspondientes. La tabla alembic_version es administrada por Flask-Migrate para registrar la revisión aplicada.

Resultado de la Parte 2. Los tres modelos fueron creados con sus relaciones uno a muchos, la migración inicial quedó versionada en el repositorio y el esquema fue aplicado correctamente en SQLite. La base puede reconstruirse desde cero ejecutando flask db upgrade.

5.3. CRUD de Médicos

El listado muestra el identificador, el nombre, la especialidad y la cantidad de citas de cada médico. Incluye búsqueda por nombre o especialidad y acciones de edición y eliminación. Si el médico tiene citas, el sistema impide la baja y muestra una advertencia.

5.4. CRUD de Pacientes

El módulo de pacientes permite registrar, buscar, editar y eliminar pacientes. El teléfono se valida con una expresión regular que admite números, espacios, paréntesis, guiones y el signo +. Al igual que en médicos, no se permite eliminar un paciente con citas registradas.

5.5. CRUD de Citas

El módulo de citas relaciona médicos y pacientes. El listado muestra la fecha, la hora, el médico con su especialidad, el paciente con su teléfono y un estado calculado (Programada, Hoy o Atendida). También permite filtrar por fecha y por médico.

Resultado de la Parte 3. Los tres CRUD están completos y las plantillas heredan de base.html. La interfaz reutiliza componentes de Bootstrap, muestra mensajes flash y ofrece búsqueda, filtros y confirmaciones de borrado.

Sección 7

Conclusiones

El sistema MediControl cumple con todos los requerimientos del segundo parcial práctico. Se implementó una arquitectura monolítica modular con el patrón Application Factory, tres Blueprints independientes y una base de datos SQLite versionada mediante migraciones.

Logros técnicos

  • Separación clara de responsabilidades entre configuración, modelos, rutas y plantillas.
  • Relaciones uno a muchos correctamente declaradas y verificadas en la base de datos.
  • Migraciones reproducibles: el esquema puede reconstruirse desde cero con un solo comando.
  • CRUD completo para las tres entidades, con búsqueda, filtros, mensajes y confirmaciones.
  • Validaciones de negocio que evitan duplicados y protegen la integridad referencial.
  • Interfaz responsiva con Bootstrap 5 y recursos almacenados localmente.

Aprendizajes

El desarrollo permitió aplicar de forma integrada los temas de la materia: creación de aplicaciones con Flask, uso de Blueprints, mapeo objeto-relacional con SQLAlchemy, migraciones de esquema con Flask-Migrate, herencia de plantillas con Jinja2 y construcción de interfaces con Bootstrap. También se reforzó la importancia de validar los datos tanto en el cliente como en el servidor.

Trabajo futuro

Como mejoras futuras se podrían incorporar autenticación de usuarios, roles (administrador, recepcionista, médico), historiales clínicos, notificaciones por correo o WhatsApp, y una API REST para integrar el sistema con otras aplicaciones.
